# RC29.21 — QR labels, portable data and backorder graphs

Release date: 2026-10-10 (Thailand/Phan Thong date basis)

## QR labels

Open **Files & Traceability → Open Work Order QR Labels**. The source is the active Plan-2026 copy shown in the source registry. The export filters by Plan-2026 section/location and the current due-date range. It includes only rows marked open with positive remaining pcs. The phone database is not used as a fallback because it can be behind the active plan.

The workbook contains:

- `Sticker Print`: A4, 3 columns × 8 labels per page; each QR and its matching uppercase WO are in the same sticker block, with the WO directly below the QR.
- `QR_LABELS`: uppercase work order, item/customer, remaining quantity, due date, section, QR payload and QR image.
- Source file name, active stored path, source modified/import time, selected section/date range and eligibility rule.

The QR content is `SLWO:<UPPERCASE WO>`. It does not encode a PC IP address. Connection-to-app QR codes remain separate. Generated label workbook and QR PNG files are saved under the selected `CENTRAL_DATA\REPORTS` and `CENTRAL_DATA\REPORTS\QR_TEMP` paths.

The date filter means **current Plan-2026 due date**, using the existing plan model’s revised delivery date with its initial-date fallback. Section means the active Plan-2026 section/location field. Labels describe planning assignment and do not prove the part’s physical location.

## Carrying data into a revised program

The ZIP deliberately excludes live `CENTRAL_DATA`. To carry forward existing audits and photos, close the current app, copy the complete existing `CENTRAL_DATA` folder into the new program folder, then launch the new program. If `<new program>\CENTRAL_DATA` exists, RC29.21 uses it before the older RC29.14 fallback. It does not clear or overwrite the copied database, photos, reports, audit register or imported source files. The former data folder is left intact.

Important folders inside `CENTRAL_DATA`:

- `DATABASE\sl_planning.db` — mobile/desktop audit events, section updates and QR scan records.
- `PHOTOS\MOBILE_AUDITS` — submitted audit photos.
- `PHOTOS\QR_SCANS` — QR scan/photo evidence.
- `REPORTS` — generated reports, dashboards and label workbooks.
- `REPORTS\QR_TEMP` — individual generated label QR images.
- `COMPANY_DATA`, `DAILY_STATUS`, `KPI`, `PRODUCTION_WIP`, `SOURCE_COPIES` — active source files and department records.

Keep a separate backup of `CENTRAL_DATA` before upgrades. Do not merge two active databases by copying files while the app is running. To move another copy’s newer audit records, use the app’s backup/migration procedure rather than overwriting a live database.

## Backorder definition and graphs

The strict backorder definition remains shared: whole-WO open (Plan-2026 EU/Packing or FC/final close rule), positive balance (`QTY − Packing Actual`), and current due date earlier than the Thailand/Phan Thong date. Due today is not overdue. Product category `F` maps to `P`. Future open orders are demand, not backorders.

Home, Backorder, Daily Planner and TV dashboard use the same `overdue_backorders`/`overdue_month_category` calculation for overdue graphs and totals. TV now shows all past-due due-month history in the overdue graph and adds a separate due-today/future graph. The future graph title explicitly says it is not backorders. Graphs show units in titles/axes and hover evidence for WOs and weight. Source filenames remain in the dashboard footer.

## Verification performed

- Python syntax compilation: `hub.py`, QR label helper, shared backorder helper and Daily Planner.
- Backorder synthetic tests: overdue/due-today/future split, closure, category F-to-P, duplicated WO and MPS year boundary.
- QR workbook tests could not run in the cloud image because the pinned `qrcode[pil]` runtime dependency is not installed there. The release installer pins it; scan quality, printer alignment and mobile decode still require a real factory label/device check.
- No live Plan-2026, Windows D: path, mobile camera or operator workload was available for factory acceptance. Treat this package as a release candidate until checked on the target PC and one printed label.
